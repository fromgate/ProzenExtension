# Задача: копирование полной схемы `zen-api.toml` из dev-сборки

## 0. Как читать этот файл

Это самостоятельное описание следующего этапа. Перед началом прочитай:

- `AGENTS.md` — правила сборки и модулей;
- `docs/api-validation.md` — текущая архитектура валидатора;
- `reference/zen-api.toml` — действующий эталон;
- `docs/tasks/OPENCODE_TASK.md` — история исходной задачи (этапы 0–4).

Работаем **поэтапно**. После каждого этапа — короткий отчёт и ожидание подтверждения.
Не коммитить `build/`, `.gradle/`, `buildSrc/build/` и per-module `build/`.

## 1. Цель

Сделать в dev-сборке вторую кнопку в настройках:

> **«Скопировать схему API (Новое: X)»**

Она копирует в буфер обмена **полный текст `reference/zen-api.toml`**, а новые поля, которых ещё нет в эталоне, дописывает в специальные секции:

```toml
[endpoints.some-endpoint.unknown]
"someField" = "number" # обнаружено 02.11.2026
#   пример: 1793394000000
```

Дальше разработчик вручную разбирает `unknown`: переносит записи в `used` или `ignored`, сохраняет файл, пересобирает расширение. При следующем копировании без новых полей должен получиться **ровно сохранённый файл**, со всеми комментариями, порядком секций и форматированием.

Это не «сериализация модели в TOML». Это **патч исходного текста**: существующий текст не переформатируется, в него только вставляются новые строки и секции.

## 2. Что уже есть и чего не хватает

Сейчас:

- `reference/zen-api.toml` компилируется `buildSrc` в компактный JSON + hash;
- в dev-бандл попадает только `ZEN_API_REFERENCE_JSON` и `ZEN_API_REFERENCE_HASH`;
- `DiffStore` хранит расхождения в `chrome.storage.local` (`diff:<hash>`);
- `CopyText.kt` формирует «почти TOML» с расхождениями, но не полный файл;
- кнопка «Скопировать расхождения (N)» живёт в `devtools/src/dev/kotlin/devtools/DevTools.kt`;
- `unknown` как отдельной категории нет: компилятор знает только `used` и `ignored`.

Не хватает:

1. Исходного текста эталона в dev-бандле.
2. Поддержки `[endpoints.<имя>.unknown]` в компиляторе, JSON, модели и валидаторе.
3. Чистой функции, которая патчит исходный TOML.
4. Второй кнопки и счётчика.

## 3. Принятые решения

### 3.1. `unknown` — временная категория

`[endpoints.<имя>.unknown]` — полноценная секция эталона, но **не** `used` и **не** `ignored`.

- Значение — тип в том же синтаксисе, что в `used`: `string`, `number`, `boolean`, `object`, `array`, `null`, `any`, объединения `A|B`, необязательность `?`.
- Пути — только точные наблюдённые пути. `[]` разрешён, `*` и `**` запрещены.
- Пустая секция `unknown` допустима: после ручного разбора её можно оставить, файл должен собираться.
- `unknown` не проверяется на тип и не порождает `missing`/`type`/`empty`: это склад для ручного разбора.
- `unknown` участвует в покрытии `new`: путь, попавший в `unknown`, больше не должен появляться как `new`.

### 3.2. Обход: `unknown` ведёт себя как `ignored` (вариант A)

Выбран вариант **A**:

- при обходе ответа `unknown` останавливает спуск, как `ignored`;
- одно новое поддерево = одна запись в `unknown` (а не все вложенные поля);
- вложенные поля видны в комментарии-примере;
- чтобы раскрыть объект, разработчик переводит родителя в `used` и пересобирает расширение.

Это сохраняет идемпотентность: после сохранения `unknown` и пересборки следующий запуск не должен добавлять детей этого объекта.

Если под `unknown`-узлом есть более специфичное правило `used`, обход должен спускаться к нему — как сейчас с `ignored`.

### 3.3. Старая кнопка остаётся

«Скопировать расхождения (N)» не удаляем. Она нужна для `missing`, `type`, `status`, `empty`, `unverified` и осиротевших записей. Схемная копия содержит только `new` → `unknown`; остальные расхождения в неё не попадают.

### 3.4. Счётчик X

`X` — количество **новых путей**, которые будут добавлены в `unknown` при этом копировании. Это не общее число `unknown` в файле.

- Считаются только `DiffRecord.kind == NEW`, не `orphaned`, для эндпоинтов, которые есть в эталоне.
- Пути, уже покрытые `used`/`ignored`/`unknown`, не считаются.
- `new-endpoint` и `new-variant` в X не входят и в схемную копию в этой задаче не добавляются.

Кнопка активна и при `X = 0`: это позволяет скопировать файл как есть и проверить round-trip.

### 3.5. Формат `unknown`-записи

```toml
[endpoints.some-endpoint.unknown]
"someField" = "number" # обнаружено 02.11.2026
#   пример: 1793394000000
```

- Тип берётся из `DiffRecord.observed`; если пусто — `any`.
- Дата берётся из `DiffRecord.firstSeen` в формате `DD.MM.YYYY`; если `firstSeen == 0` — текущая дата.
- `record.sample` добавляется отдельной строкой-комментарием, если он непустой.
- Пример обрезается до `unknownSampleLimit = 2 * 1024` символов с явным маркером `…[обрезано N симв.]`; полный образец остаётся в старом отчёте до пересборки.
- Новые записи сортируются по пути и дописываются в конец существующей `unknown`-секции.
- Существующие строки, комментарии и порядок не меняются.
- Дубли не добавляются.

### 3.6. `meta.updated` не трогаем автоматически

Схемная копия не меняет `meta.updated`, `zenVersion` и другие существующие строки. Дату обновляет человек.

### 3.7. Исходный текст эталона

Основной вариант — генерировать в `ZenApiReference.kt` ещё одну константу:

```kotlin
internal const val ZEN_API_REFERENCE_TOML: String = """..."""
```

Текст должен быть **побайтно равен** `reference/zen-api.toml` (с учётом переводов строк и финального newline). При генерации экранировать `$` для Kotlin raw-string; если в TOML когда-нибудь появится `"""`, генератор должен явно упасть, а не молча испортить текст.

Если возникнут проблемы с размером/экранированием, можно обсудить dev-ресурс и `fetch`, но это отклонение нужно согласовать.

## 4. Изменения по слоям

### 4.1. `buildSrc`

Файлы:

- `buildSrc/src/main/kotlin/zenapi/Model.kt`
- `buildSrc/src/main/kotlin/zenapi/ReferenceCompiler.kt`
- `buildSrc/src/main/kotlin/zenapi/ReferenceJson.kt`
- `buildSrc/src/main/kotlin/zenapi/KotlinSource.kt`
- `buildSrc/src/main/kotlin/zenapi/Tasks.kt`
- тесты в `buildSrc/src/test/kotlin/zenapi/`

Нужно:

1. Добавить `unknown` в `ENDPOINT_KEYS`.
2. Добавить модель `UnknownPath(path: ReferencePath, type: TypeSpec)`.
3. `EndpointDefinition` получает `unknown: List<UnknownPath>`.
4. `readUnknown()`:
   - путь через `PathSyntax.parse`;
   - запретить `AnyKey` и `Deep` (то есть `*`/`**`);
   - тип через `TypeSyntax.parse`, поддержать строку и `{ type = "..." }` как в `used`;
   - пустая таблица `unknown` допустима.
5. Проверки:
   - одинаковый точный путь в `used` и `unknown` — ошибка;
   - одинаковый точный путь в `ignored` и `unknown` — ошибка;
   - `unknown`-путь, уже покрытый родительским `ignored`, — предупреждение (избыточно);
   - `*`/`**` в `unknown` — ошибка.
6. `ReferenceJson` добавляет `"unknown": [...]` (после `ignored`), с `path`, `types`, `specificity`.
7. `Compilation` получает `source: String` — исходный текст TOML.
8. `toKotlinSource()` пишет `ZEN_API_REFERENCE_TOML`.
9. `VerifyApiReferenceTask` печатает `unknown N`.
10. Тесты:
    - разбор `unknown` и типов;
    - пустая `unknown`-таблица;
    - запрет `*`/`**`;
    - конфликт с `used`/`ignored`;
    - JSON-поле `unknown`;
    - исходный текст в сгенерированном Kotlin совпадает с входным.

Хеш эталона изменится, потому что в JSON появится новое поле `unknown` (даже пустое). Это нормально; `revalidate` сработает по смене хеша.

### 4.2. `devtools`

Файлы:

- `devtools/src/dev/kotlin/devtools/Reference.kt`
- `devtools/src/dev/kotlin/devtools/PathValidator.kt`
- новый `devtools/src/dev/kotlin/devtools/SchemaCopy.kt`
- `devtools/src/dev/kotlin/devtools/DevTools.kt`
- `devtools/src/release/kotlin/devtools/DevTools.kt` — только если понадобится новая публичная точка; сигнатуру `devSettingsSection` желательно не менять.

Нужно:

1. DTO/модель:
   - `Endpoint.UnknownRule(path, types)`;
   - `Endpoint.unknown: List<UnknownRule>`;
   - `bestUnknown(actual)` — точное совпадение пути;
   - `isCovered(actual)` учитывает `used`, `ignored`, `unknown`.
2. `PathValidator.walk()`:
   - найти `unknown` для текущего пути;
   - если `unknown` покрывает узел и под ним нет более специфичного `used`, остановиться;
   - не добавлять `unknown` в `hasMatchingIgnored`: пропавшие `used`-поля должны по-прежнему давать `missing`;
   - не проверять типы `unknown`, не порождать `empty`/`missing` для него.
3. `ReferenceHolder.sourceText` — доступ к `ZEN_API_REFERENCE_TOML`.
4. `SchemaCopy.kt` — чистые функции:
   - `newSchemaRecords(records, reference): List<DiffRecord>` — фильтр и сортировка;
   - `buildSchemaCopy(records, reference, source, today): String`;
   - `patchSchema(source, additions): String`.
5. Патчер:
   - если добавлений нет — вернуть `source` без изменений;
   - сгруппировать добавления по эндпоинту;
   - если `[endpoints.X.unknown]` уже есть — дописать строки в конец её тела;
   - если нет — создать секцию после `[endpoints.X.ignored]`; если `ignored` нет — после `used`; если нет и `used` — после `[endpoints.X]`;
   - вставлять после последней key-value строки якорной таблицы, **до** блока комментариев следующего эндпоинта;
   - сохранять стиль переводов строк (`\n` или `\r\n`) и финальный newline;
   - экранировать путь тем же `tomlEscape`, что и в `CopyText.kt`.

Точка вставки — самая хрупкая часть. Нужен небольшой построчный сканер, который понимает:

- заголовки таблиц `^\[([^\]]+)\]$`;
- key-value строки (ключи всегда в кавычках);
- комментарии и пустые строки.

Нельзя вставлять секцию после комментариев, которые относятся к следующему эндпоинту. Если сканер получится слишком хрупким — остановиться и согласовать более простой вариант (например, все `unknown` в конец файла), но не менять формат самовольно.

## 5. Этапы

### Этап 1. `unknown` в эталоне и валидаторе

- `buildSrc`: модель, парсер, JSON, проверки, тесты.
- `devtools`: `Reference.kt`, `PathValidator.kt`, покрытие `new`.
- `reference/zen-api.toml` не обязан получить реальные `unknown`-секции; можно проверить на временном примере и убрать его.
- Проверка: `./gradlew -p buildSrc test`, `./gradlew verifyApiReference`, dev-сборка.
- Остановиться, отчитаться.

### Этап 2. Исходный текст и патчер

- `ZEN_API_REFERENCE_TOML`.
- `SchemaCopy.kt` с чистыми функциями.
- Тесты/смок:
  - `patch(source, []) == source` на реальном `reference/zen-api.toml`;
  - синтетическое добавление даёт ожидаемую вставку;
  - повторный `patch` без добавлений возвращает уже пропатченный текст байт-в-байт;
  - проверка `\r\n`, финального newline, комментариев.
- Для JS-смока можно временно включить `binaries.executable()` + `nodejs()` в `devtools/build.gradle.kts`, прогнать `:devtools:jsNodeDevelopmentRun -x kotlinStoreYarnLock` с заглушкой `globalThis.chrome`, затем вернуть конфиг и удалить временный файл. Это уже проверенный в проекте приём.
- Остановиться, отчитаться.

### Этап 3. Кнопка и счётчик

- Вторая кнопка, X, уведомление, обновление по фокусу/DEBUG.
- Ручная проверка в `build/extension-dev`.
- Остановиться, отчитаться.

### Этап 4. Финальная проверка

- `./gradlew -p buildSrc test`
- `./gradlew verifyApiReference`
- `./gradlew build` (dev)
- `./gradlew -Pprozen.dev=false build`
- `./gradlew -Pprozen.dev=false checkReleaseBundle`
- Ручной round-trip:
  1. загрузить `build/extension-dev`;
  2. включить DEBUG;
  3. получить новые поля, скопировать схему;
  4. сохранить файл, пересобрать, перезагрузить расширение;
  5. скопировать схему снова — текст должен совпасть с сохранённым файлом.
- Обновить документацию.

## 6. Критерии готовности

- Кнопка «Скопировать схему API (Новое: X)» есть в dev-настройках и скрыта в release.
- При отсутствии новых полей копируется **ровно** исходный `zen-api.toml`.
- Новые поля попадают в `[endpoints.<имя>.unknown]` с типом, датой и примером.
- Существующие комментарии, порядок и форматирование сохраняются.
- После сохранения файла с `unknown` и пересборки:
  - файл собирается;
  - эти пути больше не появляются как `new`;
  - повторное копирование возвращает сохранённый текст.
- Старая кнопка расхождений продолжает работать.
- `unknown` не влияет на `missing`/`type`/`empty` для `used`.
- Release-бандл не содержит ни raw TOML, ни devtools-кода.

## 7. Вне рамок этой задачи

- Автоматический разбор `unknown` и перенос в `used`/`ignored`.
- Новые эндпоинты и варианты в схемной копии (остаются в старом отчёте).
- `missing`/`type`/`status`/`empty`/`unverified` в схемной копии.
- Объединение типов `string|null` для `unknown`: в v1 берём последний `observed`; это известное ограничение.
- Автоматическое обновление `meta.updated`.
- Удаление пустых `unknown`-секций.
- Кнопка «очистить расхождения», фильтры, значок на иконке.
