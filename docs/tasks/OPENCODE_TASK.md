# Задача для OpenCode: отслеживание изменений неофициального API Дзена

## 0. Контекст

Проект — браузерное расширение на Kotlin/JS (Ktor client, kotlinx.serialization), которое использует **неофициальное API Дзена**. Оно периодически меняется, и разработчик (я) узнаёт об этом вручную через DevTools. Нужно автоматизировать.

Выбранный подход — **рантайм-валидация внутри dev-сборки расширения**:

- Dev-сборка расширения при каждом запросе к API сверяет ответ с **эталоном** (один TOML-файл в репозитории).
- Эталон описывает, какие поля ответа код **использует** (`used`) и какие **осознанно игнорирует** (`ignored`).
- Расхождения (новое поле, пропавшее поле, смена типа, неожиданный статус, неописанный эндпоинт) копятся в `storage.local`.
- В настройках dev-сборки есть кнопка «скопировать расхождения в буфер обмена». Дальше я **вручную** вношу изменения в код и в TOML.
- В release-сборке всего этого нет.

Вместе с этим файлом лежат два черновика, которые нужно использовать как отправную точку (они могут быть неточными, проверяй по коду):

- `zen-api-reference.toml` — черновик эталона для текущего `Requester`.
- `Requester-observer-changes.kt` — черновик изменений `Requester` (интерфейс наблюдателя и единая воронка).

## 1. Правила работы

- Работаем **поэтапно**. После каждого этапа остановись, кратко отчитайся (что сделано, какие отклонения от плана, что непонятно) и дождись моего подтверждения.
- Сначала читай код, потом предлагай. Не выдумывай то, чего не видишь. Если чего-то не хватает, спроси.
- Не меняй публичные сигнатуры и поведение `Requester` сверх описанного ниже. Все отклонения явно перечисляй в отчёте.
- Dev-код (валидатор, эталон, расхождения, страница настроек) не должен попадать в release. Это обязательное требование, а не пожелание.
- Этап 3 — это **диалог**. До его завершения валидатор и интерфейс не реализуются.
- Вопросы в диалоге задавай по одному, с вариантами и своей рекомендацией, не списком из десяти пунктов.

## 2. Решения, которые уже приняты

### 2.1. Первоисточник — эндпоинт, а не функция

Одна функция `Requester` может ходить на несколько эндпоинтов, а один эндпоинт обслуживать несколько функций. Ответ принадлежит эндпоинту, поэтому описывается один раз на эндпоинт. Метки функций в эталоне не нужны; максимум они попадают в отчёты как необязательный `caller`.

### 2.2. Идентичность эндпоинта — путь и значимые параметры

```
"GET editor-api/v2/publisher/{id}/stats2?fields=impressions&groupBy=flight&total=true"
```

Ответы с разными параметрами могут сильно различаться, поэтому их описывают как **разные эндпоинты**, даже если часть полей дублируется (так проще и честнее).

Правила сопоставления реального запроса с `match`:

- Схема и хост отбрасываются. Метод — часть ключа (пока везде `GET`).
- Сегмент пути `{name}` — любой сегмент (имя только для людей).
- **Порядок параметров не важен.** Query разбирается в карту `имя → множество значений`. Порядок значений внутри повторяющегося параметра и дубли значений тоже не важны. Значения декодируются из percent-encoding. Имена параметров чувствительны к регистру.
- Литерал в `match` (`groupBy=flight`) — параметр обязан присутствовать с этим значением.
- Переменная в `match` (`from={date}`) — параметр обязан присутствовать, значение любое.
- Для повторяющихся параметров (`fields`) запись `fields=ctr` значит «набор содержит `ctr`»; `fields=ctr,vtr` — «набор содержит оба». Точного равенства набору нет.
- **Параметры, которых нет в `match`, не учитываются.**
- Среди подходящих кандидатов побеждает самый специфичный: больше литеральных параметров, затем больше параметров вообще. Ничья — ошибка сборки.
- Нормализованная строка (параметры отсортированы по имени, значения внутри параметра тоже) используется для обнаружения дублей и для вывода.

При неудачном сопоставлении различаются две ситуации:

- путь незнаком вообще → «новый эндпоинт»;
- путь знаком, но ни один вариант параметров не подошёл → «неописанный вариант».

В обоих случаях генерируется заготовка раздела из реального запроса. Параметры из `meta.volatileParams` генератор отбрасывает.

### 2.3. Формат эталона — один TOML-файл

Структура:

```toml
[meta]
format         = 1                  # версия формата
zenVersion     = "2.189.0"          # с каким Zen-Client-Experiments сверялись
updated        = 2026-10-30
volatileParams = ["page", "pageSize", "from", "to", "publisherId", "clid"]

[endpoints.<имя>]                   # имя: A-Za-z0-9_- (голый ключ TOML)
match = "GET editor-api/v3/publishers/{id}"
note  = "карточка канала"           # только для людей

[endpoints.<имя>.used]              # на что рассчитывает код
"publisher.regTime" = "number"
"publisher.metrikaCounterId" = { type = "number?", by = ["getMetrikaId"] }

[endpoints.<имя>.ignored]           # осознанно не используем; значение — причина
"publisher.*" = "прочие поля канала, пока не используем"
```

**Пути** (в `used` и `ignored`, ключи всегда в кавычках):

- `a.b.c` — вложенные объекты;
- `name[]` — любой элемент массива (`total.intervals[].timestamp`); путь может начинаться с `[]`, если корень ответа массив; `[]` без продолжения как отдельный сегмент недопустим;
- `*` — любой ключ на одном уровне (`items.*.published`);
- `**` — всё поддерево, только последним сегментом и **только в `ignored`**;
- `\.` — точка внутри имени ключа.

**Типы в `used`:** `string`, `number`, `boolean`, `object`, `array`, `null`, `any` (поле обязано быть, тип не важен).

- `A|B` — объединение (`number|null`);
- `?` в конце — поле может **отсутствовать** (`number?`). Отсутствие и `null` — разные вещи; в Kotlin-аксессорах они сливаются в `null`, а валидатору нужно различать;
- расширенная запись `{ type = "...", by = ["функция"] }`; `by` — только документация и отчёты, на валидацию не влияет. Строковая запись по-прежнему допустима.

**Значение в `ignored`** — непустая причина.

**Приоритет правил по пути:** побеждает более специфичное (больше литеральных сегментов; `*` специфичнее `**`). Одинаковая специфичность у `used` и `ignored` — ошибка сборки.

**Семантика обхода:**

- Все элементы массива сливаются в один путь (`publications[]`), тип поля — множество типов, встреченных у элементов.
- Пустой массив ничего не доказывает: для его содержимого статус «не проверено», а не «поле пропало». (Уточнено на этапе 4: если на пути массива есть явное правило, пустой массив обрабатывается по семантике `array?` / `empty`.)
- Узел-контейнер остаётся в `used` (`"publications" = "array"`), а содержимое можно игнорировать через `publications[].**`.
- Обход под `**` обрывается сразу (не нужно разворачивать большие игнорируемые поддеревья).
- Для не игнорируемых массивов в dev-сборке допустим настраиваемый лимит элементов (например, первые N и последние N).

**Категории расхождений:**

| вид | смысл |
|---|---|
| `new` | путь не в `used` и не под `ignored` |
| `missing` | путь из `used` не встретился (при непустом массиве, без `?`) |
| `type` | типы не совпали |
| `status` | статус не 200 или тело не JSON |
| `unverified` | проверить было нельзя (пустой массив без правила на пути массива, оборванный обход) |
| `empty` | ожидался непустой массив, пришёл пустой (только при строгом `array`) |
| `new-endpoint` / `new-variant` | неописанный эндпоинт / вариант параметров |

### 2.4. Как эталон попадает в расширение

- Файл один: `reference/zen-api.toml` (путь можно изменить, если в проекте есть конвенция).
- При сборке dev-варианта **Gradle-задача в `buildSrc`** парсит TOML (JVM-библиотека, например `ktoml` или `toml4j`), **валидирует** его и пишет один JSON в ресурсы dev-сборки. В release эта задача не участвует.
- Расширению парсер TOML **не нужен**. Комментарии при конвертации теряются.
- При старте dev-сборка сравнивает хеш встроенного JSON с сохранённым в `storage.local`. Не совпал — эталон перезаписывается и переоцениваются накопленные расхождения. Совпал — ничего не делается.
- Расхождения хранятся в `storage.local` отдельно от эталона, **по одному ключу на запись** (`diff:<хеш от endpoint+вид+путь>`), чтобы разные контексты расширения не затирали друг друга. Запись содержит: имя эндпоинта, вид, путь, ожидаемое и наблюдаемое, обрезанный фрагмент значения, счётчик, первое и последнее появление, `caller`.
- Переоценка при смене эталона: `new` удаляется, если путь теперь покрыт; `type` удаляется, если типы теперь допустимы; `missing` удаляется, если путь убрали из `used` или добавили `?`; записи, чей эндпоинт исчез, помечаются осиротевшими, а не удаляются.
- Кнопка «скопировать» формирует текст для вставки в TOML: по эндпоинтам, `new` сгруппированы по родителю (одна строка `"a.b.**" = ""` вместо десятков полей), пустые причины, пример значения в комментарии; для `missing`/`type`/`status`/`empty` — только комментарии, заготовок нет (там сначала правится код); заготовки разделов для новых эндпоинтов и вариантов в канонической форме `match`.

### 2.5. Как определяется режим разработчика (предварительное решение)

**Наличие модуля = режим разработчика.** Без флагов в рантайме:

- В общем коде — интерфейс `ApiObserver` и `ApiObservers.current` со значением по умолчанию `NoopObserver`. `Requester` знает только про это.
- Валидатор, матчер, хранилище, страница настроек — в **отдельном модуле `dev-validator`**, который подключает только dev-вариант.
- В dev-варианте крошечный файл при запуске ставит `ApiObservers.current = <валидатор>`. Регистрация должна выполниться **до создания первого `Requester`**.
- Поиска классов по имени в рантайме нет: в Kotlin/JS нет `ServiceLoader`, имена меняются при минификации.
- Проверка: в собранном release-бандле не должно быть строк вроде `diff:`, имён dev-классов и эталона; у release-манифеста нет `unlimitedStorage` и dev-разрешений.

Как именно это ложится на структуру нашего проекта, обсуждаем на этапе 3.

### Этап 2. Правка `Requester`

Используй `Requester-observer-changes.kt` как основу. Требования:

1. `ApiObserver`, `ApiCall`, `NoopObserver`, `ApiObservers` в общем коде.
2. Единая воронка: один запрос → текст один раз → JSON один раз → вызов наблюдателя → результат. `getJson` и `getData<T>` строятся поверх неё. Воронка внутри публичной `inline`-функции доступна через `@PublishedApi internal`.
3. Наблюдатель получает `method`, полный URL с query, статус, разобранный JSON (или `null`, если тело не JSON), необязательный `caller`. Вызывается и при статусе не 200.
4. Вызов наблюдателя в `try/catch`; наблюдатель не должен замедлять и ломать запрос.
5. Observer передаётся параметром конструктора по умолчанию `ApiObservers.current`; существующие подклассы и тесты должны компилироваться без правок.
6. Публичные методы (`getScr`, `getTimespentRewards` и т.д.) не меняются.
7. Явно перечисли поведенческие отличия от старого кода. Известные мне:
   - раньше `getJson` брал тело через ContentNegotiation и падал при неверном Content-Type, теперь тело парсится из текста;
   - в `getData` раньше использовался `Json` по умолчанию, без `ignoreUnknownKeys` (в `getJson` игнорирование включено). Сохрани как есть и отметь в отчёте, считаешь ли ты это ошибкой;
   - прямые вызовы `getHttpResponse` в обход воронки наблюдатель не видит. Найди такие места и предложи, как их перевести.
8. Мелкая чистка меток (`getStrikes` использует метку `"getStrikesInfo"`) — по желанию, отдельным коммитом.

Критерии готовности: проект собирается, существующие тесты проходят, при `NoopObserver` поведение расширения не изменилось; добавлен тест, что наблюдатель получает URL, статус и JSON и что исключение внутри него не ломает запрос.

### Этап 4. Пустые массивы (`array?`) и образцы для новых массивов

Этап выполняется после этапов 1–3. Он уточняет §2.3: пустой массив — это не всегда «не проверено», а зависит от правила на пути массива. Работаем по тем же правилам: остановка после этапа, отчёт, ожидание подтверждения.

**4.1. Семантика `array?`**

- `array?` означает «массив может отсутствовать **или** быть пустым». Двойное значение принимается осознанно: в реальных ответах Дзена пустое поле и отсутствие поля обычно значат одно и то же.
- Синтаксис менять не нужно: `?` уже разбирается в `TypeSpec.optional`. Меняется только поведение валидатора (`PathValidator`).
- Обход по пути массива, для которого есть правило:
  - строгий `array` + пустой массив → новая запись `empty` на пути массива; содержимое не проверяется, дочерние `unverified` подавляются;
  - `array?` + пустой или отсутствующий массив → тишина, без проверки содержимого;
  - `array?` + непустой массив → обычная проверка по общим правилам;
  - строгий `array` + отсутствующий массив → как сейчас: `missing` (или `unverified` при необязательном предке).
- Нет точного правила на пути массива (правила есть только на элементах) + пустой массив → поведение прежнее: дочерние `unverified` («пустой массив: содержимое не проверено»). Валидатор не выдумывает несуществующее правило.
- Обрезанный массив (больше `ARRAY_SAMPLE_SIZE = 40`) → как сейчас `unverified`; `empty` для обрезки не ставится.

**4.2. Новая категория `empty`**

- `DiffKind.EMPTY("empty")`; ожидаемое — «непустой array», наблюдаемое — «пустой массив»; путь и `caller` — как у остальных категорий.
- Автоснятие по фактическим ответам: массив стал непустым, исчез или перестал быть массивом. При `empty` и при тишине `array?` ранее накопленные дочерние `unverified` под этим массивом снимаются, иначе они зависнут навсегда.
- Переоценка при смене эталона: запись удаляется, если правило стало `array?`, удалено или закрыто `ignored`.
- В TOML-заготовку `empty` не превращается: решение принимает человек (либо `array?`, либо это баг данных/кода). В копируемом тексте — только `#`-комментарий.

**4.3. Эталон**

- `reference/zen-api.toml`: `limitations = "array?"`.
- `limitations[].url` остаётся `"string"`: прошлый отчёт был следствием пустого массива, а не отсутствия `url`.
- Остальные массивы пока не трогаем; переводим на `array?` только по фактам из `empty` после ручных прогонов.

**4.4. Миграция старых записей**

- Ранее накопленные `unverified` с причиной «пустой массив» больше не воспроизводятся. При смене хеша эталона (хеш изменится из-за `limitations`) одноразово вычистить такие записи.
- Отдельную кнопку «очистить» не вводим — она остаётся в списке «позже».

**4.5. Образцы для новых массивов**

- Для `new`, чьё значение — массив, хранить один элемент целиком в компактном JSON (последний просмотренный — допустимо; выбор элемента не принципиален, `newNodes` может остаться last-wins).
- В записи — примечание о позиции и количестве («элемент 3 из 17»), чтобы образец был анализируемым.
- Потолок образца — 16 КБ вместо 200 символов, с явным маркером обрезки; для новых объектов — тот же потолок.
- В копируемом тексте образец печатается без обрезки до 120 символов; короткие лимиты (`NEW_DETAIL_LIMIT = 12` путей) сохраняются.

**4.8. Проверка**

- `./gradlew :devtools:compileKotlinJs` по ходу, затем `./gradlew build` (dev).
- `./gradlew -Pprozen.dev=false build` + `checkReleaseBundle` — чисто.
- `./gradlew verifyApiReference` — эталон валиден, хеш изменился (зафиксировать новый в отчёте).
- `./gradlew -p buildSrc test` — зелёные; изменений в `buildSrc` не ожидается, `?` уже поддержан.
- Ручной прогон: статья с пустым `limitations` → `empty`; после появления непустого массива запись снимается; копия содержит комментарий `empty`, а новый массив — полный образец.

Критерии готовности: строгий `array` + пустой массив даёт `empty` без дочерних `unverified`; `array?` при пустом/отсутствующем молчит; без правила на пути массива поведение прежнее; старые `unverified` вычищены при смене хеша; release чист; копируемый текст остаётся paste-ready.
