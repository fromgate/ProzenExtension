# Валидация неофициального API Дзена

Краткая фиксация договорённостей. Реализация начинается только после согласования плана.

## Границы

- Валидатор существует только в dev-сборке. В release нет ни модуля, ни эталона, ни строк расхождений.
- Эталон — один файл `reference/zen-api.toml`. Расширение TOML не парсит; эталон попадает в dev-бандл как сгенерированные Kotlin-константы: JSON, хеш и исходный текст для копирования схемы.
- Валидатор ничего не правит сам: он накапливает расхождения, а правки кода и эталона делает разработчик вручную.

## Сборка

- Флаг `prozenDev` считается в корневом `build.gradle.kts` при конфигурации: `-Pprozen.dev=true|false` важнее, иначе имя задачи `buildVersion` значит release, иначе dev.
- `buildVersion` вместе с `-Pprozen.dev=true` падает на конфигурации: release нельзя случайно собрать с dev-кодом.
- `./gradlew build` → dev: `build/extension-dev`, `build/extension-zip/prozen-dev.zip`, `build/extension-zip/prozen-firefox-dev.zip`, source maps включены.
- `./gradlew buildVersion` → release: `build/extension`, `prozen.zip`, `prozen-firefox.zip`, без source maps и без devtools; перед тегом выполняется `checkReleaseBundle`.
- `:devtools` — отдельный библиотечный модуль (своего бандла нет, код входит в бандлы потребителей): реальный код в `src/dev/kotlin`, заглушки в `src/release/kotlin`, каталог выбирается флагом `prozenDev`. Модуль исключён из списка исполняемых бандлов; `getJsSourceModules(dev)` дополнительно отфильтровывает dev-only модули, если они появятся.
- `:devtools:generateApiReference` существует только в dev и компилирует `reference/zen-api.toml` в `devtools/build/generated/reference/ZenApiReference.kt`.
- Потребители: `content`, `search`, `stats`, `status` — `installDevValidator()` первой строкой `main()`; `settings` — `devSettingsSection(this)` в контейнере кнопки «Сохранить».
- `ApiObserver`, `ApiCall`, `ApiObservers`, `NoopObserver` лежат в `common`.
- Chrome dev-манифест собирается из release-копии: `"name": "Prozen dev"` и `unlimitedStorage`; `options_page` остаётся `settings.html`. Исходный манифест в репозитории не меняется. Firefox dev — обычный манифест, тот же JS.
- Защита: `checkReleaseBundle` (только release, иначе падает) проверяет отсутствие devtools-файлов, source maps, dev-строк (`ZEN_API_REFERENCE`, `volatileParams`, `new-endpoint`, `new-variant`, `unverified`, `непустой array`, `diff:`, `Prozen dev`), dev-имени и `unlimitedStorage` в манифесте.
- Каталог расширения перед копированием очищается (`cleanExtension`), чтобы старые source maps и dev-файлы не пережили смену режима.

## Формат эталона

- Один раздел = один эндпоинт (метод + путь + значимые параметры).
- `by` не используется: кто вызывает эндпоинт, видно по `caller` в расхождениях и по коду.
- `volatileParams`: `page`, `pageSize`, `from`, `to`, `addTimeFrom`, `addTimeTo`, `publisherId`, `publicationIds`, `publicationId`, `publicationIdAfter`, `query`, `language`, `clid`, `sortBy`, `sortOrderDesc`, `orderBy`, `ascending`.
- Варианты `stats2` различаются по `groupBy` **и** `fields` (иначе `getScr` и `getStatsActuality` неразличимы).
- `types` и `view` — значимые параметры, не шумовые.
- Пути: `a.b.c`, `[]`, `*`, `**` (только последним сегментом и только в `ignored`), `\.` для точки в имени ключа. В `unknown` допустимы только точные пути: `*` и `**` запрещены.
- Типы: `string`, `number`, `boolean`, `object`, `array`, `null`, `any`; объединение `A|B`; необязательность `?`. Для массива `?` значит «может отсутствовать или быть пустым», для остальных типов — только «может отсутствовать». В `unknown` записи те же, что в `used`; для новых полей пишется `number`, а не `integer`.

## Временные записи `unknown`

- `[endpoints.<имя>.unknown]` — склад наблюдённых, но ещё не разобранных полей. Разработчик переносит их в `used` или `ignored` вручную.
- Формат записи:

  ```toml
  [endpoints.some-endpoint.unknown]
  "someField" = "number" # обнаружено 02.11.2026
  #   пример: 1793394000000
  ```

- `unknown` ведёт себя как `ignored` при обходе: останавливает проверку узла и всего поддерева, но более специфичное правило `used` под ним всё равно проверяется.
- `unknown` участвует только в снятии `new`: путь в `unknown` не появляется как новый. На `missing`, `type`, `empty` и `unverified` для `used` он не влияет.
- Одинаковый путь в `used`/`ignored` и в `unknown` — ошибка сборки. Если `unknown` уже покрыт правилом `ignored`, компилятор выдаёт предупреждение.
- Пустая секция `unknown` допустима; `[]` в JSON остаётся.
- Ограничение v1: хранится только последний наблюдённый тип, объединения типов автоматически не собираются.

## Схема скомпилированного эталона

Эталон `reference/zen-api.toml` компилируется в JSON (format 1). Он встраивается в dev-бандл константой, поля короткие, потому что JSON дублируется в каждом бандле и сравнивается по хешу в `storage.local`.

```json
{
  "format": 1,
  "hash": "sha256:…",
  "meta": { "zenVersion": "2.189.0", "updated": "2026-10-31" },
  "volatileParams": ["page", "…"],
  "endpoints": [{
    "name": "stats2-flight-scr",
    "note": "текст для людей",
    "match": {
      "method": "GET",
      "segments": [{ "k": "lit", "v": "editor-api" }, { "k": "var", "v": "id" }],
      "params": [{ "n": "fields", "v": ["impressions"] }],
      "canonical": "GET editor-api/v2/publisher/{id}/stats2?fields=impressions",
      "specificity": [3, 3]
    },
    "used": [{ "path": [{ "k": "key", "n": "total" }], "types": ["object"], "optional": false, "specificity": [1, 0] }],
    "ignored": [{ "path": [{ "k": "deep" }], "reason": "…", "specificity": [0, 0] }],
    "unknown": [{ "path": [{ "k": "key", "n": "someField" }], "types": ["number"], "specificity": [1, 0] }]
  }]
}
```

- Сегменты пути: `{"k":"key","n":"…"}`, `{"k":"arr"}`, `{"k":"any"}`, `{"k":"deep"}`.
- Параметр-переменная в `match` записан как `"{имя}"`.
- `specificity`: для `match` — `[литеральных параметров, параметров всего]`, для пути — `[литеральных сегментов, "*"]`.
- `hash` — sha256 от JSON с пустым полем `hash`; комментарии и форматирование TOML на хеш не влияют.
- Одинаковые `match` (в том числе отличающиеся порядком параметров) и потенциально неоднозначные пары — ошибка сборки. Неоднозначность проверяется без реальных запросов: одинаковые метод и длина пути, совместимые сегменты, разные литеральные значения одного параметра считаются разными вариантами.

## Requester

- Единая воронка: запрос → текст один раз → JSON один раз → наблюдатель → результат.
- Наблюдатель получает метод, полный URL, статус, JSON (или `null`) и `caller`; вызывается и при статусе не 200; обёрнут в `try/catch`.
- `getData` переводится на `Json { ignoreUnknownKeys = true }`, `getPublicationStat` — под `safe()`.
- `caller` совпадает с именем функции (`getStrikes`, `getChannelData`, `getRegTime`), без прежних расхождений.
- Попадания в кеш `RequesterCached` наблюдателя не вызывают: запроса нет, наблюдать нечего.

## Валидатор

- Категории: `new`, `missing`, `type`, `status`, `unverified`, `empty`, `new-endpoint`, `new-variant`.
- Обход: элементы массива сливаются в один путь; `**` обрывает обход; количество проверяемых элементов ограничивается (первые N и последние N, `ARRAY_SAMPLE_SIZE = 40`).
- Пустой массив: если на его пути есть правило `array` (без `?`) — расхождение `empty` («ожидался непустой array»), содержимое не проверяется, дочерние `unverified`/`missing` подавляются. Если правило `array?` — тишина (отсутствие тоже допустимо). Если правила на пути массива нет (только на элементах) — прежние дочерние `unverified` («содержимое не проверено»).
- Элементы массива проверяются выборкой: при обрезанном массиве (больше `ARRAY_SAMPLE_SIZE`) — `unverified`, а не `missing`; `empty` для обрезки не ставится. Правила под пропавшим родителем не каскадируются — сообщается только предок; необязательный родитель-объект даёт `unverified`, необязательный родитель-массив (`array?`) молчит вместе с содержимым.
- `ignored` покрывает узел и все поддеревья под ним; приоритет по специфичности (`Key`-правила выше `*`/`**`). Правило `used` ниже узла, не перекрытое `ignored`, позволяет спускаться в «неизвестный» контейнер.
- `unknown` останавливает обход так же, как `ignored`, с тем же исключением для более специфичного `used` под узлом. В `isCovered` он закрывает поддерево, поэтому сохранённые `unknown`-поля не возвращаются как `new`.
- «new» сообщается одним узлом за всё новое поддерево: дальнейший обход останавливается, разворачивание происходит при выводе «почти TOML». Образец нового узла — до 16 КБ (`newSampleLimit`); для массива это один элемент целиком (последний просмотренный) с пометкой «элемент N из M». Короткий лимит 200 символов остаётся для `type`/`status`.
- `new-endpoint` / `new-variant` накапливаются со статусом 200 и телом JSON; при не-200 запоминается только `status`, чтобы ошибка сервера не создавала ложный неописанный эндпоинт. Имя неописанного эндпоинта — хвост пути в kebab-case («`{id}`» и чистые числа отбрасываются), совпадение с существующим именем устраняется суффиксом `-2`.
- Автоснятие по фактическим ответам (кроме «new»): `missing`/`unverified` — путь появился (а `unverified` под массивом с правилом — ещё и когда массив пуст или проверен целиком); `type` — типа теперь допустимы; `empty` — массив стал непустым, исчез или перестал быть массивом; `status` — на запросе с успехом.
- Хранение: отдельный ключ на запись (`diff:<хеш>`), чтобы контексты не затирали друг друга. В записи: эндпоинт, вид, путь, ожидаемое, наблюдаемое, фрагмент значения, счётчик, время первого и последнего появления, `caller`. Счётчик увеличивается при каждом повторении; ключ — FNV-1a по `endpoint|вид|путь|request`.
- При смене хеша эталона (в `storage.local` под `prozen-api-reference-hash`, перечитывается и на установке валидатора, и при открытии настроек): `new` удаляется, если путь теперь покрыт; `type` — если типы допустимы или требование убрано; `missing` — если путь помечен `optional` или убран; `empty` — если правило стало `array?`, убрано или закрыто `ignored`; `new-endpoint`/`new-variant` — если запрос теперь совпадает с эталоном; записи исчезнувших эндпоинтов помечаются осиротевшими (`orphaned`), а не удаляются. `new-endpoint` осиротевшим не становится: его имени в эталоне нет по определению. Тогда же одноразово вычищаются старые `unverified` с причиной «пустой массив», если на пути массива появилось правило: их больше не воспроизводят.
- Матчинг запроса: убираем схему/хост, сравниваем метод и сегменты пути; query разбирается в `имя → множество значений` с percent-decoding (плюс — пробел); порядок и дубли не важны. При равенстве побеждает самый специфичный `match`.

## Структура движка (`devtools/src/dev/kotlin`)

- `PathSyntax.kt` — шаги пути (`Key`/`ArrayItem` в ответе, плюс `AnyKey`/`Deep` в правилах), форматирование и парсер человекочитаемых путей, специфичность (`PathRank`: литеральные сегменты, потом `*`).
- `ActualRequest.kt` — разбор URL, query в `имя → множество значений`, канонический запрос.
- `Reference.kt` — модель скомпилированного JSON (DTO + рантайм: списки `used`/`ignored`/`unknown`, матчинг запросов, выборка правил), исходный текст эталона `sourceText`.
- `PathValidator.kt` — обход JSON, правила приоритетов, категории `new`/`missing`/`type`/`empty`/`unverified`, снимок ответа для удаления прошлых записей.
- `DiffStore.kt` — хранение `diff:<хеш>` в `chrome.storage.local`, обновление и переоценка по хешу.
- `ApiValidator.kt` — наблюдатель Requester: матч запроса, разбор неописанных эндпоинтов/вариантов, делегирование обходу.
- `CopyText.kt` — «почти TOML» для буфера обмена: чистые функции, без обращения к storage.
- `SchemaCopy.kt` — выбор непокрытых `new` и текстовый патчер полного эталона: дописывает `unknown` в исходный TOML, не переформатируя файл.
- `DevTools.kt` — установка наблюдателя, обе кнопки в настройках, переоценка по хешу в `main()`/настройках.

## Интерфейс

- Отдельной страницы нет. В `.prozen-save-button-container` рядом с «Сохранить» две кнопки: «Скопировать расхождения (N)» и «Скопировать схему API (Новое: X)».
- Кнопки приходят из dev-модуля (`devSettingsSection`); в release там заглушка, поэтому в release-бандле их нет.
- Обе видны только при `Option.DEBUG`; при выключенной отладке скрыты. `D+Numpad0` переключает режим и сразу обновляет кнопки (`refreshDevSettingsIndicator(debug)`), без перезагрузки страницы; `DebugLogger` получает новое значение синхронно.
- Счётчики обновляются при открытии настроек, при возврате фокуса на вкладку и после копирования. При нуле кнопка расхождений неактивна и показывает «Скопировать расхождения (0)». Кнопка схемы остаётся активной при `X = 0`: она копирует текущий эталон без изменений.
- Переоценка эталона по хешу выполняется при открытии настроек и перед копированием.
- Фильтры, очистка, «прогнать все запросы», значок на иконке, лимит элементов — позже.

## Копируемый текст

- Один «почти TOML», сгруппированный по эндпоинтам и отсортированный по имени; в шапке — число записей и хеш эталона.
- `new` схлопываются по родителю: одиночный путь остаётся точным (`"a.b.c" = ""`), соседи объединяются в `"a.b.**" = ""` (корень — `"**"`). Строки идут в `[endpoints.<имя>.ignored]` с пустой причиной — её заполняет человек; схлопнутые пути и примеры значений — в комментариях, не больше 12 путей (дальше «ещё N»). Пример печатается без дополнительной обрезки: образец уже ограничен 16 КБ при сохранении, у нового массива это целый элемент с пометкой позиции. Вложенные пути под уже схлопнутым родителем не дублируются.
- `missing`, `type`, `status`, `unverified`, `empty` — только `#`-комментарии с ожидаемым, наблюдаемым, `caller` и числом повторов; у `unverified` отдельной строкой причина; заготовок нет, сначала правится код.
- Новые эндпоинты и варианты — заготовка раздела с `match` из реального запроса без `volatileParams`; для известного пути переиспользуется его `{id}`-шаблон, для нового пути сегменты остаются литералами с TODO; имя — хвост пути в kebab-case, при совпадении добавляется суффикс `-2`. `used`/`ignored` в заготовке не создаются: там TODO.
- Осиротевшие записи (эндпоинта больше нет в эталоне) выводятся отдельным блоком `#`-комментариев, без TOML-разделов.

## Копирование схемы API

- Кнопка «Скопировать схему API (Новое: X)» кладёт в буфер **весь** `reference/zen-api.toml`, а не только расхождения. `X` — сколько путей будет добавлено в `unknown` этим копированием, а не общее число записей `unknown`.
- В `unknown` попадают только `new` с непустым путём, не осиротевшие и ещё не покрытые `used`/`ignored`/`unknown`. `missing`, `type`, `status`, `empty`, `unverified`, новые эндпоинты и варианты остаются в старом отчёте расхождений.
- Запись: `"путь" = "последний наблюдённый тип" # обнаружено DD.MM.YYYY`, при отсутствии типа — `any`; пример — следующей строкой `#   пример: …`, не длиннее 2 КБ и в одну строку.
- Патчер не сериализует TOML заново: он вставляет строки в исходный текст, сохраняя комментарии, порядок секций, форматирование, CRLF и наличие/отсутствие финального перевода строки. При пустом списке добавлений возвращается исходный файл байт-в-байт.
- Секция вставляется после последней key-value строки `unknown`, иначе `ignored`, иначе `used`, иначе самого эндпоинта — до комментариев следующего эндпоинта. Уже существующие пути (в том числе покрытые более общим правилом) повторно не дописываются.
- Исходный текст встроен в dev-бандл константой `ZEN_API_REFERENCE_TOML` рядом с JSON и хешем. Генератор падает, если в файле встретится `"""`, чтобы не потерять текст.
- Round-trip: сохранить скопированный файл, пересобрать расширение, скопировать схему снова — текст должен совпасть с сохранённым; сохранённые пути больше не появляются как `new`.

## Открытые вопросы

- Влияют ли `types` и `view` на форму ответа `publications-list` — проверяется наблюдением.
- Разделы `publications-list` и `publication-view-stat` до первых отчётов заполняются по `studioRequestDataToCards`, `Card` и `Stats`, то есть частично предположительно.
- Инфраструктура тестов для JS-части (`requester`, `devtools`) — решено: только JVM-тесты логики, без jsNodeTest/karma. Поэтому тест наблюдателя из этапа 2 сознательно не добавлен; проверка — компиляция и ручной прогон.
- Обмен через локальный dev-сервер — позже; хранилище расхождений и генератор текста держим чистыми функциями, чтобы экспорт добавлялся отдельно.
