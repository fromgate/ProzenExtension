# Внешние поля карточек публикаций: контракт и план

Статус: план следующего этапа. Подготовительный рефакторинг карточек (этапы 1–4) реализован; этап 5 (ручная сверка DOM) выполняется при загрузке dev-сборки.

Документ заменяет `docs/card-fields-customization.md`: старый план подготовительного этапа выполнен, а внешний контракт пересмотрен. Актуальные сведения оттуда перенесены сюда; история изменений остаётся в git. Краткая памятка для текущей разработки — в `AGENTS.md`, раздел «Publication cards».

## 1. Принятые решения

- Внешние модули передают **только данные**, а не DOM и не `render`-колбэки.
- Контракт внешних данных (`CardExtra`, `CardExtraProvider`) живёт в `common`; отдельный модуль `cards-api` сейчас не создаётся.
- `CardField`, `CardFieldRegistry`, `CardFields` и композиции остаются внутренними для `content`.
- Провайдер внешних данных — **batch**: получает пачку `Card` и возвращает данные по id публикации. Это оставляет место для будущих сетевых источников премиума.
- Первый потребитель контракта — dev-поле `status` в `devtools`.
- Премиум-модуль пока не проектируется; его источник данных неизвестен. Контракт должен позволить подключить его позже без переделки рендера.
- Размещение внешних полей: дашборд — полноширинная строка под колонками; таблица — под ER в `cells[6]`; сетка — новая строка снизу.
- Переключение `Option.DEBUG` требует перезагрузки страницы; live-перерендер не добавляется.
- В dev-режиме `status == null` отображается как `status: null` (можно заменить на `—`, это не влияет на архитектуру).

## 2. Текущее состояние

Карточки не строятся с нуля: контент-скрипт находит готовые карточки Дзена и перезаписывает блоки статистики. Три точки рендера находятся в `content/src/jsMain/kotlin/publications/Publications.kt`.

| Раскладка | Точка входа | Что перезаписывается | Зона расширения сейчас |
|---|---|---|---|
| Дашборд | `processDashboardCards()` | `div.prozen-card-stats`: 4 колонки `prozen-card-column` | Новая колонка в конце flex-ряда |
| Таблица | `modifyPublicationTable()` / `modifyTableRow()` | Ячейки `cells[3..6]`, заголовки, время в `cells[1]` | Строка под ER внутри `cells[6]` |
| Сетка | `modifyPublicationGrid()` / `modifyGridCell()` | `div.prozen-grid-card-stats`: 4 строки по 2 ячейки, дата | Новая строка снизу |

Уже реализовано:

- базовые поля вынесены в дескрипторы `CardField` (`BaseCardFields.kt`);
- три раскладки описаны композициями (`DashboardComposition`, `TableComposition`, `GridComposition`);
- работает реестр `CardFieldRegistry` и инициализация `CardFields.init()`;
- есть `CardVisibility` с константным `true` — задел под будущие настройки скрытия полей;
- зоны расширения существуют, но внешние поля в них пока не регистрируются;
- сохранены `data-prozen-publication-id`, `data-prozen-updated` и логика `waitList`.

Не меняется:

- нативные правки страницы: заголовки таблицы, время `cells[1]`, сниппет, дата в сетке;
- форматирование чисел/дат/процентов в `common/Card.kt`;
- CSS-классы в `prozen/src/jsMain/resources/css/prozen.css`;
- порядок базовых полей и DOM базовых раскладок.

## 3. Целевая архитектура

Три уровня не смешиваются:

| Уровень | Что это | Где живёт | Кто владеет |
|---|---|---|---|
| `Card` | Модель публикации: id, статус, статистика, время | `common` | `common` |
| `CardExtra` | Данные для внешнего отображения: текст, иконка, tooltip, порядок | `common` | внешний модуль формирует, `content` рисует |
| `CardField` | Внутренний дескриптор базового поля с рендером и действиями | `content` | `content` |

### 3.1. `CardExtra` — данные внешнего поля

Минимальный набор:

| Поле | Назначение |
|---|---|
| `id` | Уникальный id с префиксом: `dev.status`, `premium.plan` |
| `text` | Готовый текст; `null` — текста нет |
| `iconCssClass` | CSS-класс иконки; `null` — иконки нет |
| `title` | Tooltip/полное значение |
| `order` | Порядок вывода; меньшее значение — выше |

Правила рендера:

- есть текст и иконка — рисуются оба;
- есть только текст — рисуется текст;
- есть только иконка — рисуется иконка с `title`;
- нет ни текста, ни иконки — поле пропускается;
- несколько `CardExtra` у одной карточки дают несколько строк в зоне расширения.

Контракт остаётся data-only. Ссылки, картинки по URL, произвольный DOM и действия добавляются только при появлении реального потребителя, а не заранее.

### 3.2. `CardExtraProvider` — batch-провайдер

Провайдер получает пачку `Card` и возвращает `Map<publicationId, List<CardExtra>>`.

- Провайдер сам решает, что показать: существующие поля `Card`, вычисленные значения или данные из нового источника.
- Если данных нет или модуль выключен, возвращается пустая карта.
- Ошибка провайдера логируется, но не ломает рендер карточек: `content` продолжает без его данных.
- Порядок провайдеров — порядок регистрации; внутри карточки `CardExtra` сортируются по `order`, затем по `id`.
- Дубликаты `CardExtra.id` в пределах одной карточки отбрасываются; приоритет у первого.
- Идентификаторы внешних полей всегда строковые и namespaced. Базовые `CardFieldId` для внешних полей не используются.

### 3.3. Загрузчик и рендер в `content`

- Новый загрузчик `CardExtras` опрашивает всех зарегистрированных провайдеров один раз на пачку карточек.
- `Publications` получает данные до рендера и передаёт в композиции уже готовый список `CardExtra` для конкретной карточки.
- `CardComposition` больше не принимает `List<CardField>` для зоны расширения; зона расширения рендерит `CardExtra`.
- Контейнер зоны расширения создаётся только если у карточки есть хотя бы одно `CardExtra`. Пустых строк и колонок не остаётся.
- Рендер иконки/текста использует классы текущей раскладки (`prozen-card-icon` / `prozen-card-text` или `prozen-grid-card-icon` / `prozen-grid-card-text`).
- `CardField`, `CardFieldRegistry`, `CardVisibility` и базовые композиции не меняют свою роль: они отвечают только за стандартные поля.

### 3.4. Базовые поля остаются внутренними

Внешний модуль не получает `CardField` и не рисует DOM. Это снимает вопрос #6 из старого документа: `devtools` и будущий премиум зависят только от `common`, а `content` зависит от них. Цикла нет.

Если позже понадобится кастомный UI, контракт расширяется осознанно: либо дополнительными data-полями, либо отдельным hybrid-механизмом с `render` для сложных модулей. Сейчас такого механизма нет.

## 4. Размещение внешних полей

| Раскладка | Решение | Запасной вариант |
|---|---|---|
| Дашборд | Полноширинная строка под четырьмя колонками (`flex-basis: 100%` или отдельный класс) | Вернуться к пятой колонке, если строка не понравится |
| Таблица | Под ER в `cells[6]` | Новая строка `<tr>` под ячейкой с заголовком, если текущее место окажется тесным |
| Сетка | Новая строка снизу | Расти больше некуда; оставляем как есть |

Внешние поля не сдвигают базовые колонки и не меняют фиксированные индексы ячеек таблицы.

## 5. Текущий объём работ

### Этап 1. Контракт в `common`

- Добавить `CardExtra` и `CardExtraProvider` в пакет `common.cards`.
- Не добавлять отдельный Gradle-модуль и не трогать `settings.gradle.kts`.
- Не переносить в `common` `CardField`, `CardFieldRegistry`, `CardRenderState` и DOM-рендер.

Проверка: `./gradlew :common:compileKotlinJs`.

### Этап 2. Загрузчик и рендер в `content`

- Добавить `CardExtras` — загрузку, слияние, сортировку и дедупликацию данных провайдеров.
- Переделать зону расширения `CardComposition` на `CardExtra`.
- Подключить загрузку в `Publications.kt` для дашборда, таблицы и сетки; данные загружать один раз на пачку и переиспользовать в `waitList`.
- Сохранить `CardField` и базовые композиции без изменений.

Проверка: `./gradlew :content:compileKotlinJs`.

### Этап 3. Размещение в дашборде

- Сделать зону расширения дашборда полноширинной строкой под колонками.
- Проверить, что базовая раскладка и DOM не изменились при пустой зоне расширения.

### Этап 4. Dev-поле `status`

- В `devtools/src/dev` добавить провайдер `dev.status`.
- Текст: `status: <значение>`; при `null` — `status: null`.
- Видимость: только при включённом `Option.DEBUG`; иначе провайдер возвращает пустую карту.
- В `devtools/src/release` — пустая заглушка регистрации.
- В `content` подключить регистрацию провайдера рядом с `CardFields.init()`.
- Не добавлять `STATUS` в `CardFieldId`: поле должно остаться внешним и попасть в зону расширения.

### Этап 5. Проверка

1. `./gradlew :content:compileKotlinJs`.
2. `./gradlew build`, загрузить `build/extension/prozen-chrome-dev`.
3. Проверить три раскладки при включённом `Option.DEBUG`:
   - дашборд — строка `status: ...` под колонками;
   - таблица — строка под ER;
   - сетка — новая строка снизу.
4. Проверить `status` со значениями `published`, `banned` и `null`.
5. Проверить, что при выключенном `DEBUG` внешних полей и пустых контейнеров нет.
6. Проверить, что базовые поля, кнопки «ссылка»/«репост», tooltip'ы и старые форматы работают как раньше.
7. Собрать release-вариант и убедиться, что dev-провайдер и его текст отсутствуют в бандле.

### Этап 6. Документация

- Обновить этот файл по фактическому результату.
- Обновить `AGENTS.md`, раздел «Publication cards», если что-то изменится по ходу реализации.

## 6. Что не входит в текущую разработку

- Настройки скрытия/показа базовых полей.
- Live-перерендер при смене настроек или `DEBUG`.
- Премиум-модуль и его источник данных.
- Ссылки, картинки по URL, произвольный DOM, кастомный `render`.
- Отдельный `cards-api`.
- Новая строка таблицы и именованные места вроде `TITLE_BADGE` / `COVER_BADGE`.
- Сортировка/упорядочивание полей пользователем.

## 7. Будущие расширения

### 7.1. Настройки скрытия базовых полей

- Добавить boolean-опции в `common/Options.kt` с id вида `card-field-shows`, `defaultValue = true`, группа «Карточки».
- В `CardVisibility` добавить маппинг `CardFieldId -> Option` и пакетное чтение перед рендером.
- Страница настроек подхватит опции автоматически.
- Применение на лету не требуется: после смены настроек — перезагрузка.

### 7.2. Премиум-модуль

- Подключается как ещё один `CardExtraProvider`; рендер `content` не меняется.
- Если данные локальные — достаточно batch-провайдера, который просто проходит по `Card`.
- Если данные с сервера — провайдер сам отвечает за запрос, кэш и таймауты; контракт уже batch.
- Если премиуму нужен `Requester`/токен, зависимости передаются в модуль при его создании или регистрации, а не через общий контракт `CardExtra`.
- Отдельно решить: код премиума поставляется всем и включается по лицензии или собирается отдельным flavor.
- Отдельно решить, как доставляются CSS/иконки премиума: общий `prozen.css`, ресурсы модуля через build-шаг или `imageUrl`.

### 7.3. Кастомный UI

Если data-контракта не хватит, добавить hybrid-вариант: `CardExtra` по умолчанию плюс необязательный кастомный рендер для сложных модулей. Это осознанное расширение API, а не текущая задача.

## 8. Открытые вопросы

1. Источник данных премиума пока неизвестен. Batch-контракт покрывает и локальные, и сетевые источники; уточняется при проектировании премиума.
2. Поставка премиум-кода: всем пользователям с runtime-лицензией или отдельной сборкой.
3. Доставка CSS/иконок премиума.
4. Нужна ли отдельная строка таблицы вместо размещения под ER — решается после ручной проверки.
5. Нужны ли внешним полям ссылки/картинки/действия — решается при первом реальном потребителе.
